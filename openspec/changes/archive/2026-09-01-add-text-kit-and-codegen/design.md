## Context

工具集里已经有三个「单页多标签 + 纯前端计算」形态的工具——`convert`（十二个转换器）、`crypto`（五个面板）、`sql-kit`（四个面板），它们共用一套已被验证的结构：

- `lib/<tool>/result.ts`——每个工具**各有一份**结构相同的 `{ ok, value?, error? }` 结果类型。`lib/sql-kit/result.ts` 的顶部注释把这条写成了明确决策：「刻意不跨工具 import：三个工具应能各自独立演进，避免一方改动波及另一方」
- `lib/<tool>/*.ts`——纯函数，不抛异常给 UI，失败走 `error`
- `components/<tool>/shared.tsx`——面板框架、输入框、下拉、复制按钮、错误条
- `components/<tool>/*.tsx`——各面板，标签切换时保留输入
- CSS 类以工具前缀命名（`cv-` / `ck-` / `sq-`）

本次要接的「文本工具」在形态上与它们完全一致，真正需要想清楚的只有三件事：

1. **与既有工具的功能边界**。`convert` 已有 JSON⇄YAML、Base64、URL、正则测试；`sql-kit` 已有 CSV/JSON → `INSERT` 并自带一份 CSV 解析器（`lib/sql-kit/csv.ts`，有 `csv.test.ts` 覆盖）。新工具很容易和它们撞车。
2. **CSV 解析要不要共用**。共用与上面那条「刻意不跨工具 import」的既有决策看似冲突。
3. **类型代码生成本质上是在「猜」**。JSON 样本不含类型信息，推断规则必须定死并且对用户诚实。

## Goals / Non-Goals

**Goals:**

- 与 `convert` / `sql-kit` 的功能边界清晰，同一件事只有一处实现，用户在错误的面板里能被指引到正确的工具
- CSV 解析算法在整个仓库只保留一份，同时不破坏「各工具结果类型独立」的既有决策
- 命名风格转换的分词规则明确、无歧义，边界情况由单测锁死
- 类型推断的规则可预期，推断不出来的地方**显式告诉用户**而不是静默给一个看似合理的类型
- 全部计算在浏览器完成，不出网、不落库；超出处理规模时给可读提示而非卡死页面
- 所有转换逻辑为纯函数，可脱离 UI 单测

**Non-Goals:**

- 不重复实现 `convert` 与 `sql-kit` 已覆盖的转换
- 不做文件上传下载、不解析 `.xlsx` 二进制
- 不做类型定义 → JSON 的反向生成，不做 IDL（Protobuf / Avro / Thrift）生成
- 不引入任何解析器或代码生成第三方库
- 不做 Web Worker 与增量计算——超出规模上限的场景应当写脚本，而不是用一个工具页硬扛

## Decisions

### 决策一：提取 CSV 解析算法到中立模块，但结果类型仍各工具独立

**选择：** 把 `lib/sql-kit/csv.ts` 中的解析实现移到 `lib/shared/csv.ts`，该模块**不依赖任何工具的结果类型**——解析失败时抛出携带可读 message 的错误。`lib/sql-kit/csv.ts` 保留原有的 `parseCsv(text, options): SqlResult<CsvTable>` 签名，内部 `try/catch` 包装共享实现；`lib/text-kit/table.ts` 以自己的 `TextResult` 同样包装。

**理由：** 这里要同时满足两条看起来矛盾的约束，关键在于区分**共享类型外壳**与**共享算法实现**：

- `result.ts` 是二十行的类型与两个构造函数。复制一份的成本近乎为零，换来的是工具间零耦合——这是既有决策的正确取舍，本次不动它。
- CSV 解析是上百行的真实算法，要处理引号包裹、转义双引号、字段内换行、分隔符选择、首行表头。复制一份意味着以后修一个引号转义的 bug 要在两处修，且很可能只修了一处——这是真实的 DRY 违规，与前者不是同一类问题。

中立模块不 import 任何一方的结果类型，这一点是决策成立的前提：`sql-kit` 与 `text-kit` 之间仍然没有依赖关系，两者只是各自依赖一个更底层的、不属于任何工具的模块。既有决策想避免的「一方改动波及另一方」并未发生。

**被否方案一：** `text-kit` 直接 `import { parseCsv } from "@/lib/sql-kit/csv"`——建立了工具间的横向依赖，正是既有决策明确要避免的形态。

**被否方案二：** 照抄一份到 `lib/text-kit/csv.ts`——把一个上百行的算法复制第二遍，是本项目 DRY 原则下不可接受的。

**迁移的安全边界：** 这次改动会触碰已经上线的 `sql-kit`，所以约束是硬的——`lib/sql-kit/csv.test.ts` **不做任何修改**即须全部通过。测试文件一旦需要改动，说明这不再是纯移动，应当中止并重新评估。

### 决策二：命名风格转换先分词后重组，一份分词器 + 八个重组器

**选择：** 不实现「风格 A → 风格 B」的两两转换，而是统一走 `分词 → 重组` 两步：任意输入先归一化为词数组 `string[]`，再按目标风格重组。

**理由：** 八种风格两两互转是 56 个函数，且每加一种风格增加 16 个；分词加重组是 1 + 8 个函数，每加一种风格只增加 1 个。更重要的是，两两转换的实现里「怎么切词」这件事会被写 56 遍，规则必然漂移——而切词恰恰是这件事里唯一有难度的部分。

**分词规则必须定死**（这是本决策的实质内容，每一条都进单测）：

| 规则 | 输入 | 分词结果 |
| --- | --- | --- |
| 按显式分隔符切分（`_` `-` 空格 `.`） | `foo_bar-baz qux` | `foo` `bar` `baz` `qux` |
| 小写→大写边界切分 | `fooBarBaz` | `foo` `Bar` `Baz` |
| 连续大写后接小写时，在最后一个大写前切分 | `HTTPServer` | `HTTP` `Server` |
| 字母后紧跟数字**不切分** | `address1` | `address1` |
| 数字后接大写字母切分 | `user2Name` | `user2` `Name` |
| 连续分隔符产生的空词丢弃 | `foo__bar` | `foo` `bar` |
| 混合形式按以上规则叠加 | `foo_barBaz` | `foo` `bar` `Baz` |

「字母后紧跟数字不切分」这条是刻意的：`address1` / `line2` / `md5` 这类命名极其常见，切开会得到 `address_1`、`md_5`，与所有主流工具和人的直觉都不符。而 `user2Name` 里数字后面的大写 `N` 已经构成了一个独立的词边界信号，所以那里要切。

### 决策三：批量替换只做「应用」，正则「测试」留在编码转换

**选择：** 本工具的替换面板输入「原文 + 匹配 + 替换 + 选项」，输出替换后的完整文本与替换次数。不提供匹配高亮、捕获组表格、分组预览这类调试视图——那是 `convert` 的正则测试面板的职责，面板内给出一句指引。

**理由：** 两者用途不同：调试正则时你想看「匹配到了什么、第 2 组捕获了什么」，应用替换时你只想要结果文本。把调试视图也搬过来，等于把 `convert` 的正则面板复制一遍，且两份实现会各自演进。边界按**用途**切而不按**技术**切——虽然底层都是 `RegExp`。

**非法正则的处理：** 前置捕获 `new RegExp()` 抛出的异常并转为可读错误，不让 UI 崩溃；这与 `convert` 侧的处理保持一致的用户体验。

### 决策四：表格转换以「二维表格」为中枢模型

**选择：** 定义中枢模型 `{ header: string[]; rows: string[][] }`，CSV/TSV、JSON 数组、Markdown 表格各实现一个 `parse` 与一个 `stringify`，所有转换都走「源格式 → 中枢 → 目标格式」。

**理由：** 三种格式两两互转是 6 个方向（含双向），直接实现要 6 个函数；走中枢是 3 个 parse + 3 个 stringify = 6 个——数量看似持平，但差别在扩展性与一致性上：新增一种格式，直接实现要加 6 个函数，走中枢只加 2 个；而且所有格式共享同一套「表头缺失怎么办、单元格数量不齐怎么办」的处理，不会出现「CSV→JSON 补空串、Markdown→JSON 却报错」这种不一致。

**JSON 侧的约定：** JSON 数组转表格时，列取所有对象字段的并集（与 `datastore` 的 `ResultPanel` 同一取向），缺失字段留空；嵌套对象与数组单元格序列化为紧凑 JSON 文本，不递归展开成多列。

### 决策五：类型推断的规则定死，推断不出来的显式告知

**选择：** 推断规则如下表，并在生成结果之外**单独输出一份「需人工确认的字段」清单**。

| 输入情形 | 处理 |
| --- | --- |
| 对象数组 | 取所有元素的字段**并集**；未在全部元素中出现的字段标记为**可选** |
| 数组元素类型不一致（如 `[1, "a"]`） | 元素类型降级为「任意」，并列入需确认清单 |
| 值为 `null` | 类型不可推断，标记为可空的「任意」类型，并列入需确认清单 |
| 空数组 `[]` | 元素类型不可推断，列入需确认清单 |
| 空对象 `{}` | 生成一个空类型，列入需确认清单 |
| 整数超出 JavaScript 安全整数范围 | 按 64 位整数生成（Java `Long` / Go `int64`），并列入需确认清单 |
| 含小数点的数值 | Java `Double` / Go `float64` / TS `number` |
| 嵌套对象 | 生成具名子类型，名称由字段名 PascalCase 化并去复数（`items` → `Item`） |
| 子类型命名冲突 | 追加数字后缀（`Item2`、`Item3`） |

**理由：** JSON 样本里没有类型信息，任何生成器都在猜——区别只在于**是否承认自己在猜**。一份样本里 `"amount": null` 到底是数字还是字符串，工具无从知道；如果静默生成一个 `String amount`，用户很可能直接用了，等到线上反序列化失败才发现。所以本工具的选择是：给一个不会误导的保守类型（「任意」），同时把这个字段显式列出来。这份清单是本功能真正的价值所在，比多支持一门语言重要得多。

「数组字段取并集且缺失即可选」这条与 `datastore` 的表格列并集、Mongo 的字段采样推断是同一取向的延续：**面对异构数据，用并集而非首元素**，且明确标注这是推断而非权威 schema。

**目标语言首版四种**：TypeScript `interface`、Java POJO（纯字段 + 注释，不预设 Lombok 或任何注解框架）、Go `struct`（带 `json` tag）、JSON Schema。Java 侧不生成注解是刻意的——注解风格与团队约定强相关，生成了大概率要删。

### 决策六：处理规模设硬上限，超出即拒绝并说明

**选择：** 输入文本设体积上限、JSON 设嵌套深度上限，超出时前置拒绝并给出可读提示（说明上限值与建议）。不引入 Web Worker，不做增量计算。

**理由：** 这些计算全部同步跑在主线程上，没有上限的话，一份几十兆的文本或者一个病态嵌套的 JSON 会直接把标签页卡死——用户看到的是浏览器无响应，连错误提示都收不到。设上限的代价是极少数大输入被拒，收益是工具永远不会「假死」。

不上 Web Worker 是 YAGNI：需要处理几十兆文本的场景，本来就应该写个脚本，而不是往一个浏览器工具页里粘。真出现这类需求再说。

### 决策七：面板状态在标签切换间保留

**选择：** 各面板的输入与结果为页面级状态，切换标签不重置，与 `sql-toolkit` 已确立的行为一致。

**理由：** 实际用法常常是「在表格转换里整出一份 JSON，切到代码生成里生成实体类」，切一次标签就清空会让这个动作没法完成。

## Risks / Trade-offs

- **CSV 解析迁移触碰已上线的 `sql-kit`** → 纯移动不改逻辑，`lib/sql-kit/csv.test.ts` 零修改必须全绿；测试一旦需要改动即中止并重新评估。

- **分词规则存在真实歧义**（`HTTPServer`、`user2Name`、`address1`） → 规则在决策二中逐条定死，每条都有对应单测；规则表同时写进面板的说明文案，让用户知道工具是怎么切的。

- **类型推断本质是猜** → 不追求完备，而是保守取值 + 显式列出需人工确认的字段；文案上不称其为「schema」，避免用户当作权威。

- **与 `convert` / `sql-kit` 的边界会被用户误撞**（比如在文本工具里找 Base64） → 相关面板放置一句指引，说明该能力在哪个工具；边界按用途划分并写进规格，不靠口头约定。

- **主线程同步计算** → 硬上限 + 可读拒绝提示（决策六）。

- **Markdown 表格格式宽松**（对齐行、转义竖线、单元格数量不齐） → 解析取宽松策略：容忍缺失的对齐行、按最长行补空单元格；无法解析时报可读错误而非静默产出错位表格。

- **生成的 Java / Go 代码不保证可直接编译**（字段名可能是语言关键字、可能以数字开头） → 对非法标识符做转义并保留原名映射（Go 靠 tag、Java 靠注释说明），列入需确认清单。

## Migration Plan

无数据库变动、无依赖新增、无既有工具的行为变更（`sql-kit` 仅内部实现位置调整，对外签名不变）。回滚只需移除 `/text-kit` 相关文件、还原 `lib/sql-kit/csv.ts` 并撤掉导航中的一行。

任务分两段落地：

1. **第 1~4 组**：结果类型与面板外壳、CSV 提取与回归、行处理 / 命名转换 / 批量替换 / 表格转换 / 统计五个面板。此处「文本工具」已可独立验收上线。
2. **第 5~6 组**：类型推断与四种目标语言的代码生成。

与前几次变更相同的分段理由：第一段就能拿到可用工具，也避免堆出一个难以验证的巨型变更。

## Open Questions

- 是否给「接口调试」的响应区加一个「送到代码生成」的入口？能把「拿到报文 → 生成 DTO」这条链打通，但涉及跨工具状态传递，与 SQL 工具「送到查询台」是同一类问题，一并留待后续统一考虑。
- 代码生成的目标语言是否需要补 Kotlin / Rust / Python dataclass？首版四种覆盖当前主要使用场景，按实际需要再加——分词与推断层已经与目标语言解耦，新增一种只是加一个重组器。
- Java 侧是否需要可选的 Lombok / Jackson 注解开关？首版不做（决策五），若多数使用者都要手动补注解则再议。
