## Context

工具集当前有 7 个工具，其中 `/convert`（编码转换）与 `/crypto`（加解密）确立了「单页多标签 + 纯函数库 + 组件层只做渲染」的模式：`lib/<tool>/*.ts` 提供返回 `ConvertResult<T>` 的纯函数并配单测，`components/<tool>/*.tsx` 消费结果渲染输出或红色错误条，转换逻辑不向 UI 抛异常。

`components/crypto/shared.tsx` 的注释里写明了一条既定取舍：**各工具自建 `shared.tsx` 与自有 CSS 前缀，有意接受少量重复**，理由是跨工具共享组件会让一个工具的改动波及另一个，违背 `tool-shell` 规格中「新增工具不影响既有工具」的约束。本设计沿用该取舍。

本次变更全部落在纯客户端计算，无服务端 API、无数据库 schema 变更、无连接管理，因此风险面集中在两处：新引入的两个第三方依赖，以及浏览器 `TextEncoder` 只支持 UTF-8 这一硬性限制对「编码排查」的影响。

## Goals / Non-Goals

**Goals:**
- 新增 `/sql-kit` 工具页，提供参数填充、格式化、IN 列表、INSERT 生成四类 SQL 文本处理
- 为 `/convert` 增补 Cron 解析、ID 解析、编码排查、进制运算四个转换器
- 所有计算在浏览器完成：不出网、不落库、不新增服务端路由
- 每个纯函数模块配 vitest 单测，边界与非法输入均有覆盖
- 零改动既有工具的行为与路由

**Non-Goals:**
- 不做 SQL 执行——`/sql-kit` 只处理文本，连接与执行属于未来的关系型数据库客户端
- 不做 SQL 语法校验或方言兼容性检查，格式化失败即原样返回并提示
- 不支持「文本 → GBK 字节」方向（见决策 4）
- 不做 cron 的 Quartz 扩展语法（`L` / `W` / `#`）保证，仅保证标准 5/6 段
- 不做 ID 生成，只做反解

## Decisions

### 决策 1：`/sql-kit` 独立成页，而非并入 `/convert`

`/convert` 已有 8 个标签，再塞 4 个 SQL 面板会让标签栏溢出且语义混杂（编码转换 vs SQL 加工）。独立页遵循 `tool-shell` 的「新增工具只需在 `TOOLS` 注册表追加一条」扩展点，互不影响。

**替代方案**：全部塞进 `/convert`——放弃，标签栏将达 12 项，且 SQL 面板需要的双输入框布局与现有转换器的 IO 布局差异较大。

### 决策 2：`/sql-kit` 面板同时挂载、CSS 控显隐；`/convert` 新增标签沿用「只渲染当前」

两页行为不同是有意的：SQL 面板里用户会粘贴大段 SQL 与参数日志，切走再切回丢失代价高，故学 `/crypto` 的同时挂载方案；而 `/convert` 现有八个标签一律只渲染当前，新增四个若改成同时挂载会造成同一页内行为不一致，故保持现状不动既有实现。

### 决策 3：引入 `sql-formatter` 与 `cron-parser`，不自研

- **SQL 格式化**需要完整词法分析（字符串字面量、注释、方言关键字），自研必然出错；`sql-formatter` 纯 JS、无原生模块、支持 mysql/postgresql/mariadb/tsql 等方言
- **cron 下次执行时间**的难点在 day-of-month 与 day-of-week 的 OR 语义、月末与闰年边界，自研正确性风险高；`cron-parser` 纯 JS、体积小

两者均可在客户端打包，不破坏「纯客户端」约束。字段级人话描述（如 `*/5 * * * *` → 「每 5 分钟」）自研，因为它只需拆分字段做字符串描述，且现成库多为英文。

**风险**：`cron-parser` v4（`parseExpression()`）与 v5（`CronExpressionParser.parse()`）API 不兼容。实现时按 `package.json` 锁定的实际版本适配，并在 `lib/convert/cron.ts` 内用单一适配函数封装，UI 层不直接接触库 API。

### 决策 4：编码排查——UTF-8 编码原生做，GBK 方向用 `TextDecoder` 反查表

浏览器 `TextEncoder` 按规范**只支持 UTF-8**，而 `TextDecoder` 原生支持 gbk / gb18030 / big5 等。这决定了三件事：

1. **字节视图**只展示 UTF-8 / UTF-16 / Latin-1 三种编码的字节（全部原生可算）
2. **GBK 字节 → 文本**方向支持（`TextDecoder('gbk')`）
3. **乱码还原**需要「把乱码字符编回字节」，即 TextEncoder 不支持的方向。解法是**用 `TextDecoder` 惰性构建字符→字节反查表**：把 `0x81..0xFE × 0x40..0xFE` 的双字节组合连同单字节 ASCII 一次性解码，得到该编码的完整反查 Map，缓存复用。约 32K 项，构建一次数十毫秒，无需任何依赖。

**还原候选范围**限定为：原编码固定 UTF-8，误解码编码取 `latin-1 / gbk / gb18030 / big5` 四种，另加 `gbk 字节被按 UTF-8 读` 的反向候选。理由是 99% 的中文乱码属于这几类；穷举全部编码组合会产出大量噪声结果。每个候选按「U+FFFD 替换字符占比 + CJK 字符占比」打分排序，并明确标注**含 U+FFFD 的乱码不可逆**（信息已在误解码时丢失）。

**替代方案**：引入 `iconv-lite`——放弃，浏览器端打包体积约 200KB，且只为一个方向的边缘需求。

### 决策 5：SQL 参数填充必须做占位符扫描，不能用 `split('?')`

`?` 可能出现在字符串字面量（`where name = 'a?b'`）、单行注释（`-- ?`）、块注释（`/* ? */`）中。直接按 `?` 切分会整体错位，产生看似正确实则参数全错的 SQL——比报错更危险。因此 `lib/sql-kit/fill.ts` 内置一个轻量扫描器，跳过 `'...'`（含 `''` 转义）、`"..."`、`` `...` ``、`--` 到行尾、`/* */`，只收集真正的占位符位置。

参数类型映射：`Integer` / `Long` / `Double` / `BigDecimal` / `Boolean` 等数值布尔类型不加引号；`String` / `Timestamp` / `Date` / `Time` 等加单引号并把内部 `'` 转义为 `''`；字面量 `null` 原样输出。**占位符数量与参数数量不一致时报错并给出两侧数量**，不做部分填充。

输入形态同时支持「SQL 与参数分两个输入框」与「整段粘贴含 `Preparing:` / `Parameters:` 的日志自动拆分」，后者是实际使用中最省事的路径。

### 决策 6：雪花 ID 的 epoch 与位宽可配置

各家实现的起始纪元与位分配不同（Twitter 原版 epoch 为 `1288834974657`，国产实现常自定义），写死会给出错误的时间。设计为：epoch 输入框 + 预设下拉（Twitter 原版 / Unix 零点），位宽三项可配（时间戳位 / 机器位 / 序列位，默认 41 / 10 / 12），总位数超过 63 时前置校验报错。解析一律走 `BigInt`，避免 Number 精度丢失。

ObjectId 走另一条独立路径：24 位十六进制，前 4 字节为秒级时间戳，规则固定，无需配置。两者由输入格式自动分流（24 位 hex → ObjectId，纯数字 → 雪花），也允许手动指定。

### 决策 7：CSV 解析自研一个 RFC4180 子集

`INSERT 生成`只需处理逗号分隔、双引号包裹、`""` 转义、字段内换行四种情况，约 40 行代码即可覆盖，不值得为此引入解析库。分隔符可配（逗号 / Tab / 分号），首行是否为表头可选。

## Risks / Trade-offs

- **[归档顺序依赖]** 未归档的 `add-jsonpath-extract` 已 MODIFIED `encoding-toolkit` 的「工具挂载与面板布局」（七→八个转换器），本变更基于其结果继续改为十二个转换器 → **必须在 `add-jsonpath-extract` 归档之后再归档本变更**，否则该 requirement 会被回改为「八个转换器」。ADDED 的部分不受影响。
- **[新依赖引入风险]** 两个第三方库进入运行时依赖 → 均为纯 JS 无原生模块，安装后在 `lib/` 内用适配函数封装，UI 不直接依赖库 API；若将来需替换只改一个文件。
- **[反查表构建开销]** 乱码还原首次触发时构建 32K 项 Map 可能有可感知延迟 → 惰性构建 + 模块级缓存，仅在用户实际点击「尝试还原」时触发，且只构建候选涉及的编码。
- **[TextDecoder 编码支持差异]** 部分浏览器对 big5 / gb18030 的支持可能缺失 → 构建反查表前先探测 `new TextDecoder(enc)` 是否抛错，不支持的候选静默跳过并在结果区标注，不影响其他候选。
- **[SQL 参数填充的正确性边界]** 扫描器无法覆盖全部方言的字符串语法（如 PostgreSQL 的 `$$...$$` 美元引用）→ 界面明确标注「填充结果仅供人工核对与手动执行，请勿直接用于生产写操作」，并在数量不匹配时硬报错而非猜测。
- **[cron 扩展语法]** Quartz 的 `L` / `W` / `#` 等扩展语法在标准 cron 库中可能不被支持 → 解析失败时给出可读提示并指明不支持扩展语法，不静默产出错误的执行时间。

## Migration Plan

无数据迁移。新增文件为主，改动仅限三处追加式修改（`Navigation.tsx` 的 `TOOLS` 数组、`app/convert/page.tsx` 的 `TABS` 数组、`app/globals.css` 追加 `sqlk-*` 与新转换器所需样式）。回滚即移除新增文件与这三处追加，既有工具不受牵连。
