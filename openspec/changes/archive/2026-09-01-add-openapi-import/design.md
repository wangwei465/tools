## Context

「接口调试」已经具备了导入所需的全部下游设施，本次要做的是把一份 OpenAPI 文档接到这些设施上：

- `api_nodes`——邻接表（`parent_id`）存 `folder` 与 `request` 两类节点，请求定义放在节点的 `definition` JSON blob 里（见 `api-collection-tree` 与 `api-saved-requests`）
- `api_environments` + `api_variables`——环境的单激活切换，变量分「激活环境级 > 全局级」两层
- `components/api-client/vars.ts`——请求组装管线最前段做 `{{变量}}` 替换
- `api-curl-import`——已有的导入形态：解析一条 cURL → `RequestDraft` → 载入**新 tab**
- `request-auth`——bearer / basic / apiKey 三类鉴权配置

与 cURL 导入的关键差别决定了本次的形态：cURL 导入产出**一个请求**，落点是 tab；OpenAPI 导入产出**一棵树**，落点是 `api_nodes`。两者除了「导入」这个词之外几乎没有共用面，不应勉强复用同一条路径。

**一个先验风险已验证排除：** OpenAPI 的路径参数写作 `/users/{id}`（单花括号），而本工具的变量语法是 `{{var}}`。查 `components/api-client/vars.ts:10` 的 `VAR_RE = /\{\{\s*([^}]+?)\s*\}\}/g`，匹配要求双花括号，单花括号不会被误替换。因此导入时保留 `{id}` 原样是安全的，无需转义。

## Goals / Non-Goals

**Goals:**

- Swagger 2.0 与 OpenAPI 3.0 / 3.1 三种文档都能导入，版本差异对下游完全透明
- 面对真实世界里质量参差的文档（缺 tags、缺 example、`$ref` 断链、带厂商扩展），**逐项降级而非整体失败**，并如实告知降级了什么
- 导入产物直接可用：切环境即可换目标服务，无需再手工改 URL
- 写入具备原子性——要么整棵树建成，要么什么都不留
- 解析层全部为纯函数，不依赖网络与数据库，可脱离 UI 与真实文档单测

**Non-Goals:**

- 不做增量同步 / diff 合并、不做 URL 拉取、不解析外部 `$ref`
- 不导入响应定义、不生成测试断言与 Mock
- 不做导出方向，不做 Postman / Insomnia / HAR 导入
- 不追求覆盖 OpenAPI 规范的每个角落（`callbacks`、`links`、`discriminator` 的多态展开等）——这些在调试场景里用不到

## Decisions

### 决策一：归一化为中间模型，两代文档各写一个读取器

**选择：** 定义与 OpenAPI 版本无关的中间模型（大致为「服务信息 + 服务器列表 + 安全方案 + 操作列表」，每个操作含 method / path / 分组名 / 显示名 / query 参数 / header 参数 / 请求体示例），`read-v2.ts` 与 `read-v3.ts` 各自把原始文档读成这个模型，下游（分组、建树、生成环境）只认中间模型。

**理由：** 两代文档的差异集中且可枚举，但分布在很多字段上：

| 关注点 | Swagger 2.0 | OpenAPI 3.x |
| --- | --- | --- |
| 服务地址 | `host` + `basePath` + `schemes` | `servers[]` |
| 请求体 | `parameters` 中 `in: body` | `requestBody.content[mediaType]` |
| 内容类型 | `consumes` | `requestBody.content` 的键 |
| Schema 位置 | `definitions` | `components/schemas` |
| 安全方案 | `securityDefinitions` | `components/securitySchemes` |
| 表单参数 | `parameters` 中 `in: formData` | `requestBody` 的 `multipart/form-data` |

如果不归一化，这六处差异会渗进分组、建树、示例生成、环境构造等每一段下游逻辑，每段都要写一次 `if (isV2)`。归一化之后差异只存在于两个读取器里，下游代码对版本无感——这与 `datastore` 用「二维表格中枢模型」收敛格式差异是同一手法。

**被否方案：** 引入 `swagger2openapi` 之类的转换库先把 2.0 升成 3.0——多一个依赖、多一层不可控的转换语义，且转换失败时的错误信息对用户毫无意义。两个读取器加起来的代码量并不比适配一个转换库多。

### 决策二：只接受粘贴文本，不做 URL 拉取

**选择：** 导入对话框只有一个文本框，接受 JSON 或 YAML 原文（YAML 走既有依赖 `js-yaml`）。不提供「输入 swagger.json 地址自动拉取」。

**理由：** 拉取看似方便，实际引入的是一个由用户完全控制目标地址的服务端出网请求——这就是 SSRF 的标准形状，在一个会被放在开发机上、可能还开着端口的本地工具里，这个面不值得开。而用户从浏览器打开 Swagger UI 复制 JSON 只是多一步操作。

**代价与缓解：** 大文档粘贴体验一般（几百 KB 的文本框）→ 文本框做体积上限校验并给出可读提示；不引入文件上传（那是另一条需要处理临时文件的路径，同样不值得为便利开）。

### 决策三：分组用「tags 优先 → path 首段兜底 → 未分类」三级回退

**选择：** 根文件夹以 `info.title` 命名；其下每个操作按此顺序确定所属文件夹：

1. 操作的第一个 `tag`
2. 无 tag 时，取 path 的第一段（`/api/user/list` → `api`；若首段是 `api`/`v1`/`v2` 这类无信息量的前缀则顺延取下一段）
3. path 也取不出时归入「未分类」

**理由：** `tags` 是文档作者的显式分组意图，Swagger UI 本身就按它分组，用户对这个结构有肌肉记忆，优先用它最符合直觉。但内部服务的文档相当比例没有认真写 tags——此时按 path 首段分组仍然能得到一棵有意义的树，比把两百个接口平铺在一个文件夹里强得多。跳过 `api` / `v1` 这类前缀是因为它们对每个接口都相同，用它分组等于没分组。

**不做可切换的分组策略选项：** 三级回退已经覆盖了实际情形，加一个下拉让用户在导入前选「按 tag / 按 path」，是把一个工具能自己判断的事推给用户（YAGNI）。

### 决策四：重复导入新建带后缀的根文件夹，不做合并

**选择：** 导入时若已存在同名根文件夹，新建 `<title> (2)`、`<title> (3)`，并在导入前的预览里明确提示「已存在同名集合，将新建副本」。

**理由：** 自动合并需要一个稳定的「同一个接口」身份标识。`operationId` 理论上担得起这个角色，但实际文档里它经常缺失、经常重复、经常在重构后变化；退而用 `method + path` 又会在路径调整时把同一个接口判成两个。更麻烦的是合并策略本身：用户手工改过的请求体、加过的 header，在合并时是保留还是覆盖？任何一种选择都会在某些场景下丢掉用户的工作。

新建副本是笨办法，但它的失败模式是「多了一棵树，用户删掉即可」，而合并的失败模式是「用户攒了半天的请求被静默覆盖」。在这个取舍上，笨而安全优于聪明而危险。**这也是明确的非目标**，写进规格避免后续被当作缺陷。

### 决策五：servers 生成环境与 `baseUrl` 变量，URL 写成 `{{baseUrl}}/path`

**选择：** 每个 server 生成一个环境（名称取 `description`，缺失时取 host），并在该环境下建 `baseUrl` 变量指向其 URL；所有请求的 URL 统一写成 `{{baseUrl}}` + path。已存在同名环境时不覆盖，改用带后缀的名称并列入导入报告。

**理由：** 这是让导入产物「直接可用」的关键一步，也是本变更真正的价值放大点。把绝对地址硬编码进两百个请求，换个环境就得批量改；接到既有的环境切换与变量替换上之后，切一次下拉就能把整批请求指向另一套部署——而这套设施本来就已经存在，导入只是把它用起来。

**不覆盖同名环境**是因为用户的既有环境里可能有其他变量与配置，导入一份文档不应当有权改动它们。

### 决策六：`$ref` 只解析文档内部，循环引用按深度截断

**选择：** 解析 `#/` 开头的文档内引用；外部引用（含文件路径或 URL）不解析，按断链降级——该字段生成占位值并列入报告。解析时维护引用路径栈，命中循环时截断为占位对象，并设全局深度上限。

**理由：** 外部 `$ref` 要么需要读本地文件、要么需要出网，两者都与决策二的取舍相悖。而循环引用在真实文档里非常常见（树形结构、双向关联），不处理就是无限递归直接把页面搞死——这是必须处理而非可选优化的一项。

**截断优于报错：** 一个含循环引用的 schema，把循环处截断后剩下的部分仍然是有用的示例请求体；因为一处循环就拒绝整个文档的导入，是把工具的洁癖变成用户的成本。

### 决策七：降级项汇总为一份导入报告，而不是逐条弹窗或静默吞掉

**选择：** 解析过程中每一处降级都记录一条（类型 + 位置 + 说明），导入完成后集中展示为报告，列出：无 tag 而按 path 分组的操作数、`$ref` 断链的字段、无法推断请求体的操作、含路径参数需手工替换的请求、被重命名的环境。

**理由：** 真实文档几乎不可能零降级，所以「有降级就报错中止」是不可用的；但静默吞掉又会让用户在半小时后才发现某个请求体是空的，且不知道为什么。集中报告在这两者之间：导入照常完成，代价一次性讲清楚。

这与 `type-codegen` 的「需人工确认清单」是同一个设计取向——**工具在猜的地方要明说自己在猜**。

### 决策八：示例请求体的生成不与「文本工具」的代码生成共用

**选择：** `lib/api-client/openapi/sample.ts` 独立实现「schema → 示例 JSON」，不复用「文本工具」的类型推断代码。

**理由：** 两者方向相反且输入不同：`type-codegen` 是「JSON 样本 → 类型定义」，这里是「OpenAPI Schema Object → JSON 样本」。而 OpenAPI 的 Schema Object 并不等于 JSON Schema——3.0 有自己的 `nullable`、`discriminator`、`xml`，3.1 才对齐 JSON Schema，2.0 又是另一套子集。把这些差异塞进一个通用推断器，会让两边都变复杂。

生成优先级：`example` / `examples` 里的显式示例 > `default` > 按 `type` 与 `format` 生成占位值（`string`/`date-time` 给形如时间的占位、`integer` 给 `0`、`boolean` 给 `false`、`enum` 取第一个值）。有显式示例就用显式的，这一条能显著提升导入产物的可用度。

### 决策九：批量写入走单事务

**选择：** 在 `lib/db/index.ts` 新增批量建节点的事务函数，一次导入的全部文件夹、请求节点、环境与变量在同一事务内写入，任一步失败整体回滚。

**理由：** 一份文档可能生成数百个节点，中途失败留下半棵树是最糟的状态——用户既不知道导入了多少，也不好清理。`better-sqlite3` 的同步事务在这里正合适，无需额外机制。

**预览与上限：** 写入前展示将创建的文件夹数与请求数供用户确认，并设操作数量上限，超限时拒绝并提示——避免一份异常文档生成上万个节点。

## Risks / Trade-offs

- **真实文档质量参差**（缺 tags、缺 example、`$ref` 断链、厂商扩展） → 逐项降级 + 集中报告（决策七）；解析器对未知字段一律忽略而非报错。

- **大文档生成数百节点** → 单事务写入（决策九）+ 导入前预览确认 + 数量上限。

- **路径参数 `{id}` 与变量语法形近** → 已验证 `vars.ts:10` 的正则要求双花括号，单花括号不会被误替换；保留原样并在报告中统计含路径参数的请求数，提示需手工替换。

- **循环引用导致无限递归** → 引用路径栈 + 深度上限 + 截断占位（决策六），且必须有对应单测。

- **重复导入产生冗余树** → 明确为非目标（决策四），预览阶段提示「将新建副本」，让用户在写入前就知道会发生什么。

- **`operationId` 缺失或重复导致节点名无意义** → 节点名取 `summary` > `operationId` > `method + path` 三级回退，保证任何情况下都有可读名称。

- **YAML 解析的边界** → 复用既有 `js-yaml`，解析失败给可读错误并指出是 YAML 语法问题，与「这不是一份 OpenAPI 文档」区分开。

- **文档版本判定** → 依 `swagger: "2.0"` 与 `openapi: "3.x"` 字段判定；两者都缺失时明确报「无法识别的文档格式」，不做猜测式解析。

## Migration Plan

`app.db` 零表结构变动——复用 `api_nodes` / `api_environments` / `api_variables`。既有的 cURL 导入、集合树、环境与变量管理行为均不变，本次只是新增一条产出这些数据的路径。回滚只需移除导入入口与 `lib/api-client/openapi/*`，已导入的数据作为普通节点继续可用。

任务分两段落地：

1. **第 1~4 组**：中间模型、两代读取器、`$ref` 与示例生成、建树与分组——纯函数层完整且单测覆盖，此时尚未接入 UI。
2. **第 5~7 组**：事务写入、导入对话框与预览报告、验收。

先把纯函数层做扎实再接 UI，是因为本变更的复杂度几乎全在解析上；解析层一旦有单测锁住，UI 层就只是拼装。

## Open Questions

- 是否需要支持 `multipart/form-data` 与 `application/x-www-form-urlencoded` 请求体的导入？首版按 JSON 请求体生成，表单类型的操作降级为空 body 并列入报告；若实际文档里占比高再补。
- 全局 `security` 与操作级 `security` 覆盖关系是否需要精确还原？首版只取全局安全方案映射到 Auth 配置，操作级差异列入报告。
- 导入后是否需要一个「按 tag 折叠/展开」的浏览优化？取决于实际导入规模，先看使用反馈。
