## Context

全新项目，无既有代码。目标是搭建一个可持续扩展的"常用工具集合"Web 系统，并交付第一个工具——数据比对工具。核心使用场景是**比对两个接口返回的 JSON**：判断是否一致，并在不一致时清楚地定位差异。后期计划支持"直接填接口 URL、由系统代理拉取后再比对"。

## Goals / Non-Goals

**Goals:**
- 搭建可低成本挂载多个工具的系统外壳。
- 交付数据比对工具：字符串/JSON 双模式、格式化展示、hash 计算、差异定位与展示。
- JSON 采用**语义比对**（规范化后 hash），差异以 JSON Path 定位，支持扁平/树形双视图。
- 架构为"后端代理拉取接口"预留位置。

**Non-Goals:**
- 本次**不实现**通过 URL 拉取接口的代理功能（仅预留架构位）。
- 不做用户系统、登录、数据持久化/历史记录。
- 不做数组"顺序无关"的集合式比对（默认顺序敏感）。
- 不做多于两方（三方及以上）的比对。

## Decisions

### 技术栈：Next.js（React + TypeScript）
选 Next.js 而非纯前端 Vite，因为后期"接口代理"需要后端能力，Next.js 的 API routes 可在同一项目内承载，避免维护两套工程。工具集以 App Router 下的独立路由组织，新增工具 = 新增一个路由页面。

### 输入区：CodeMirror 6，而非 textarea
"格式化展示"需要缩进、语法高亮、错误标注、大对象折叠，textarea 无法满足。CodeMirror 6 相比 Monaco 轻量得多，适合在工具集中多处嵌入。

### 三层数据处理分离
同一份 JSON 在工具中被处理三次，职责必须分离，避免相互干扰：
- **格式化（展示层）**：仅用于输入区美化，保留用户输入的 key 顺序，不参与比对。
- **规范化（计算层）**：key 排序 + 压缩空白，作为 hash 与 diff 的输入。
- **差异（结果层）**：基于规范化结构做字段级 diff。

关键推论：即使两侧格式化后 key 顺序不同，只要值相同，hash 依然相等——因为算 hash 前先规范化。

### Hash 策略
JSON 模式按规范化后的字符串计算，字符串模式按原始文本计算。算法采用 SHA-256（优先 Web Crypto `crypto.subtle`，纯前端即可完成，无需后端）。

### 规范化规则
- 对象 key 递归排序。
- 压缩无意义空白。
- 数组**顺序敏感**（JSON 数组本为有序结构，且顺序无关比对复杂度高，属未来可选开关）。

### 差异定位与展示
以 JSON Path（如 `user.address.city`、`items[2].price`）定位，优于行号——接口返回常为压缩单行，行号无意义。差异分三类：值不同 / 右侧多出 / 右侧缺失。提供两种视图：
- **扁平路径列表**：逐条列出所有差异点，适合差异少、快速浏览。
- **树形高亮**：保留 JSON 结构、在变化节点高亮，适合结构复杂、需要上下文。
字符串模式无"树"的概念，视图切换禁用，退化为逐行 diff。

### 非法 JSON 处理
非法或截断的 JSON：标注错误位置、暂停比对（不算 hash、不出差异），引导用户先修正，而非强行比对产生误导结果。

## Risks / Trade-offs

- **数组顺序敏感** 可能不符合某些"只关心元素集合"的场景 → 作为未来可选开关，本次不做，符合 KISS/YAGNI。
- **树形高亮 + JSON Path diff** 是实现复杂度最高的部分（递归、嵌套、增删改标注）→ 可先交付扁平视图打通链路，再补树形视图。
- **CodeMirror 学习/集成成本** → 相比 Monaco 已是更轻选择，收益（格式化/高亮/错误标注）明确。
- **后端代理预留** 若过度设计会违背 YAGNI → 本次仅保证架构不阻塞（选型支持 API routes），不写具体代理代码。
